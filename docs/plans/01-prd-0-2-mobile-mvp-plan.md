## 1. Контекст и цель

PRD 0.2 меняет продукт: вместо одного персонального ассистента с 11 уровнями, календарём, документами и расписаниями — мобильный MVP для учителей. Формула: обучение + практика = работающий ИИ-агент. Нужно: несколько изолированных агентов (≤ 5), один маршрут из 7 уроков, 2 реальные модели, 1 управляемый MCP «Материалы», 2 скилла, серверный harness с подтверждениями, лимитами и трассой «Как выполнено».

Состояние кода (проверено):
- **Builder** — Flutter, Riverpod, go_router, sqflite. Агентный цикл выполняется на устройстве: сообщения, трасса, инструменты и разрешения хранятся локально (`lib/features/chat/infrastructure/persistent_chat_repository.dart`, `lib/features/tools/infrastructure/persistent_tools_repository.dart`, `lib/features/trace/infrastructure/persistent_trace_repository.dart`). Сервер только стримит ответ модели (`lib/features/chat/infrastructure/chat_stream_client.dart` → `POST /builder/chat/completions`). Цикла `tool_calls` нет.
- **backend** — FastAPI + SQLAlchemy async (`backend/app/core/database.py`), модели через OpenRouter (`backend/app/modules/models_and_chat.py`), есть утилита идемпотентности (`backend/app/core/idempotency.py`), авторизация (`backend/app/core/security.py:get_current_user`), демо-MCP с каталогом уроков (`backend/app/modules/mcp.py`), модули `calendar.py`, `schedules.py`, `documents.py`.
- Единственный экран ассистента: `/assistant/...` в `Builder/lib/app/router/app_router.dart`. Курс — 11 уровней в `Builder/lib/features/course/domain/course_catalog.dart`.

Результат: приложение проходит сценарий T01 из PRD на реальных вызовах моделей и MCP, проверки T02–T09 записаны с фактическими результатами.

### 1.1. Принятые решения
- **Выполнение агента — на сервере Lab** (PRD R01, R05, §6). Клиент становится тонким клиентом над API агентов и запусков. Локальный sqflite остаётся кэшем экранов и черновиков (§7 «Нет сети»). Лимиты, подтверждения, идемпотентность и изоляцию обеспечивает сервер, клиент их только отображает.
- **Сервер развивается в `backend/`** (FastAPI), без смены стека: PRD не требует конкретного стека.
- **Сначала очистка**: исключённые функции удаляются полностью, а не скрываются флагами — это упрощает схему и тесты.
- **Локальная схема хранения начинается заново** (новая версия схемы; пользовательские данные пилота ещё не существуют). Миграция старых данных ассистента не делается.
- **Интерфейс — русский.** Новые строки обязательны в `app_ru.arb`; `app_kk.arb` не удаляется до решения владельца (Q-4).
- **Код фаз — `LM` (Lab MVP)**: `LM00…LM07`. Префиксы `F`/`B`/`EF`/`EB` заняты прежним планом, а `F01–F09` — ещё и кодами требований PRD.

### 1.2. Вне рамок
- Голосовой ввод и разговор; произвольные MCP; импорт скиллов и выполнение пользовательского кода; публичные агенты и маркетплейс.
- Фоновое автономное выполнение, расписания, напоминания, календарь, push-уведомления.
- Генерация и разбор DOCX/PDF.
- Административный редактор курса (уроки обновляются конфигурацией).
- Монетизация и публикация в магазинах.
- Публикация в ChatGPT Edu (М10) — отдельная задача после подтверждения формы у организатора; здесь готовится только пакет (паспорт, инструкция ≤ 10 шагов, протоколы тестов).

## 2. Решение

### 2.1. Серверная модель данных (`backend/app/modules/lab/` — новый пакет)
Сущности по PRD §6: `agents` (owner_id, name, task_type, subject, grade, epoch, deleted_at), `agent_versions` (снимок: model_id, instruction, skills+версии, разрешения save/search, лимиты), `skills` + `skill_versions` (2 записи каталога), `agent_skill_overrides` (разрешённая часть текста), `materials` (owner_id, agent_id, title, text, source: text|photo), `photo_uploads` (TTL 24 ч), `memory_entries`, `conversations`, `messages`, `runs` (agent_version_id, epoch, status, stop_reason, idempotency_key), `run_events`, `pending_actions` (params_hash, expires_at), `course_progress` (по owner_id), `usage_ledger` (расходы).

### 2.2. API (префикс `/lab/v1`)
- Агенты: `GET/POST /agents`, `GET/PATCH /agents/{id}`, `POST /agents/{id}/copy`, `POST /agents/{id}/reset`, `DELETE /agents/{id}`.
- Конфигурация: `GET /models` (флаги `supports_tools`, `supports_vision`), `GET /skills`, материалы, фото (`POST /agents/{id}/photos` → извлечённый текст), память.
- Запуски: `POST /agents/{id}/runs` (заголовок `Idempotency-Key`), `GET /runs/{id}` (+ события), `GET /runs/{id}/stream` (SSE), `POST /runs/{id}/cancel`, `POST /runs/{id}/actions/{action_id}` (approve/deny).
- Курс: `GET/PUT /course/progress`.
- Каждый обработчик проверяет `owner_id` через `get_current_user`; чужой объект → 404.

### 2.3. Harness
Сборка контекста: правила платформы → инструкция агента → включённые скиллы → разрешённые фрагменты и память. Цикл: модель → `tool_calls` → проверка, что инструмент разрешён в снимке версии → для `save_material` создаётся `pending_action` и запуск ждёт подтверждения (таймер 60 с остановлен) → вызов MCP → результат модели. Лимиты: 3 вызова, 60 с активного выполнения, 15 мин на подтверждение. События запуска с epoch агента; после сброса поздние события отбрасываются. Логику сборки переносим из `Builder/lib/features/chat/domain/context_assembler.dart`.

### 2.4. MCP «Материалы»
Переписываем `backend/app/modules/mcp.py`: убираем `LESSON_CATALOG`, оставляем протокол JSON-RPC и добавляем `save_material(title, content)` → `material_id` и `search_materials(query)` с фильтром по `(owner_id, agent_id)` из контекста запуска (не из аргументов модели).

### 2.5. Клиент Builder
- Новый слой данных `lib/features/agents/` (domain/infrastructure/presentation): `LabApiClient` поверх `lib/core/network/`, репозитории агентов, запусков, материалов, памяти.
- Роуты: `/course`, `/course/lesson/:lessonId`, `/agents`, `/agents/:agentId/chat`, `/agents/:agentId/settings/...`, `/agents/:agentId/runs/:runId`.
- Переиспользовать: `auth`, `session`, `profile`, `ui_kit`, `share_plus`, экраны `trace`, `memory`, `instructions` как основу; `ChatController` из `lib/features/chat/chat_providers.dart` переводится на `POST /runs` + SSE.
- Новый пакет для фото: `image_picker` (камера запрашивается только при выборе фото).

## 3. Фазы реализации

### Фаза 0: Очистка исключённых функций (LM00)
**Цель:** удалить из клиента и сервера всё, что PRD 0.2 исключил, сохранив рабочую сборку.
- Builder: удалить `lib/features/calendar/`, `lib/features/schedules/`, `lib/features/documents/`; провайдеры `calendarReminderAutoSyncProvider`, `pushLifecycleProvider` в `lib/app/app.dart`; роут `/automation/runs/:runId`; таблицы `calendar_*`, `document_work` из `lib/core/storage/schema/storage_schema_v1.dart`.
- Builder: удалить уровни 8–11 и `course_automation_lesson.dart`, `automation_practice_*`; темы `comingSoon`; `text_extractor.dart` и форматы pdf/docx; старые инструменты в `lib/features/tools/domain/tools_registry.dart` и `builder_calendar_adapter.dart`; категории моделей, разделитель категории в `ChatController.sendMessage`, `suggestAlternative`.
- Builder: удалить пакеты `flutter_local_notifications`, `timezone`, `firebase_core`, `firebase_messaging`, `archive`, `xml`, `open_filex` и Firebase-конфиги Android/iOS.
- Builder: удалить или переписать тесты удалённых функций.
- backend: удалить `calendar.py`, `schedules.py`, document-jobs/artifacts из `documents.py`, `/builder/search`; обновить `tests/test_api_contracts.py`.

**Критерий приёмки (LM00):** в `Builder/` — `flutter analyze` без ошибок, `flutter test` зелёный, `flutter build apk --debug` собирается; `rg "calendar|schedules|firebase|docx" Builder/lib` не находит кода удалённых функций; в `backend/` — `pytest` зелёный.

### Фаза 1: Серверные агенты, версии и изоляция (LM01)
**Цель:** сервер хранит нескольких агентов пользователя с версиями конфигурации и строгой изоляцией по владельцу.
- Пакет `backend/app/modules/lab/`: модели SQLAlchemy из §2.1 (без runs), Alembic или текущий `create_all` из `app/main.py`.
- API агентов: создание (лимит 5 активных → `409 agents.limit-reached`), изменение (новая `agent_version`), копирование (только конфигурация), сброс (очистка памяти, материалов, диалогов агента, `epoch += 1`, отмена активных запусков), удаление (идемпотентное, освобождает слот).
- Каталоги: `GET /models` с двумя моделями из настроек и флагами совместимости; `GET /skills` с двумя скиллами и версиями.
- `course_progress` по `owner_id`, не затрагивается сбросом и удалением агента.
- Лимиты текста: инструкция и скилл ≤ 5 000, фрагмент ≤ 10 000 знаков → `422` до запуска.

**Критерий приёмки (LM01):** pytest-тесты: пользователь B получает 404 на любой объект пользователя A; шестой агент → 409; копия не содержит памяти и материалов; сброс агента 1 не меняет агента 2 и прогресс курса; повторное удаление → 204 без побочных объектов.

### Фаза 2: Серверный runtime — запуски, harness, подтверждения (LM02)
**Цель:** реальный цикл модель → инструмент → модель с лимитами, подтверждениями, идемпотентностью и событиями.
- Таблицы `runs`, `run_events`, `pending_actions`, `usage_ledger`.
- `POST /agents/{id}/runs` со снимком текущей версии и `Idempotency-Key` (переиспользовать `app/core/idempotency.py`); повтор возвращает тот же запуск.
- Harness (§2.3): сборка контекста в зафиксированном порядке, tool-loop через OpenRouter, отклонение неразрешённого инструмента, лимиты 3 вызова / 60 с / 15 мин, `stop_reason`, отмена.
- Подтверждения: `pending_action` с `params_hash`; изменённые параметры требуют нового подтверждения; просроченное не исполняется; отказ не создаёт запись.
- SSE-поток событий и `GET /runs/{id}` для восстановления после фона; события без секретов и скрытых рассуждений.
- Блокировка несовместимых сочетаний (фото/инструменты при модели без поддержки) до вызова модели; без скрытой замены модели.
- Журнал расходов и бюджет пилота с понятной остановкой.

**Критерий приёмки (LM02):** pytest с подменой провайдера модели: 4-й вызов инструмента → `stop_reason=tool_limit`; повтор с тем же ключом не создаёт второй запуск и сообщение; отказ подтверждения → записи нет; поздние события после сброса не записываются; ручной прогон против двух реальных моделей возвращает ответ.

### Фаза 3: MCP «Материалы», фото, память и скиллы на сервере (LM03)
**Цель:** реальные инструменты и данные агента, которыми пользуется harness.
- Переписать `backend/app/modules/mcp.py`: `save_material`, `search_materials` с изоляцией по `(owner_id, agent_id)` из контекста запуска; ID материала в событиях трассы.
- Раздельные разрешения save/search в версии агента; при выключенном поиске материалы не попадают в контекст автоматически.
- Фото: проверка JPEG/PNG по сигнатуре, ≤ 10 МБ, извлечение текста (способ — Q-3), удаление исходника через 24 ч; текст возвращается на проверку, а не сохраняется автоматически.
- Память: CRUD записей; удалённая запись исключается из поиска и нового контекста; URL из материалов не исполняются.
- Скиллы: включение и правка разрешённой части как новая ревизия; объяснение коллизий правил.

**Критерий приёмки (LM03):** pytest: `save_material` возвращает ID, `search_materials` в новом диалоге находит его, другой агент или пользователь не находит; фото 11 МБ и GIF под видом JPEG → 422; удалённая запись памяти отсутствует в контексте следующего запуска; скилл без разрешения инструмента не даёт вызвать инструмент.

### Фаза 4: Клиент — несколько агентов и «Мои агенты» (LM04)
**Цель:** Builder работает с агентами сервера: список, создание, копирование, переименование, сброс, удаление.
- `lib/features/agents/`: `LabApiClient`, `AgentsRepository` (сервер + кэш sqflite), Riverpod-провайдеры с текущим `agentId`.
- Новая версия локальной схемы: кэш агентов и черновики, `agent_id` во всех агентных таблицах; прогресс курса отдельно.
- Экран «Мои агенты»: список, задача, последнее использование, счётчик «X из 5», действия; диалоги подтверждения сброса и удаления с описанием последствий.
- Мастер «Подготовка заданий»: имя, предмет, класс, требования → видимая редактируемая инструкция со счётчиком 5 000.
- Роутер: `/agents`, `/agents/:agentId/...`; удалить единственный `/assistant` и `PersistentAssistantRepository.resetAssistantWorkspace`.

**Критерий приёмки (LM04):** widget-тесты: создание двух агентов, копирование без памяти, сброс одного не меняет второго и прогресс, шестой агент показывает сообщение о лимите; ручная проверка на устройстве после перезапуска приложения.

### Фаза 5: Клиент — диалог, настройки агента и «Как выполнено» (LM05)
**Цель:** пользователь настраивает агента и выполняет реальные запуски с подтверждениями и трассой.
- Чат: `ChatController` на `POST /runs` + SSE, `Idempotency-Key` на отправку и повтор, стоп, явный повтор, причина ошибки и следующий шаг, «Копировать» и «Поделиться», переключение версий ответа «до/после».
- Карточка подтверждения действия, видимые лимиты и причина остановки.
- Восстановление запуска по `AppLifecycleState.resumed` через `GET /runs/{id}`; без сети — черновик и объяснение, без скрытой очереди.
- Настройки агента: модель (2, совместимость, блокировка до отправки), инструкция (краткие поля + полный текст), материалы (текст ≤ 10 000; фото через `image_picker` → проверка и правка текста; экран маршрута обработки), скиллы (2), память (просмотр и удаление), инструменты save/search.
- «Как выполнено»: версии инструкции и скиллов, модель, фрагменты, инструмент и параметры, ID материала, статус, длительность, ошибки; сохранение после отмены видно и удаляемо.
- Доступность: масштабирование текста, подписи для screen reader, статусы текстом, сохранение черновиков.

**Критерий приёмки (LM05):** widget-тесты с подменой API: двойное нажатие «Повторить» шлёт один ключ; отказ камеры сохраняет черновик; несовместимая модель блокирует отправку; ошибка инструмента не показана как успех. Ручной прогон на устройстве: шаги 2–8 T01 проходят против сервера.

### Фаза 6: Курс из 7 уроков, плеер урока и аналитика (LM06)
**Цель:** учебный маршрут учителя с практикой, которая завершается по реальному событию.
- `course_catalog.dart`: 7 уроков PRD §2; уроки задаются конфигурацией; прогресс на сервере, обновление курса не стирает прогресс.
- `LessonPlayerPage`: объяснение → прогноз → одно изменение агента → реальный запуск (шаг закрывается событием запуска, не «Далее») → сравнение с прогнозом → самостоятельное задание.
- Урок 7: второй агент без мастера, вторая модель, собственная проверка.
- Компоненты агента открываются после знакомства в уроке и остаются редактируемыми.
- Аналитика §9 без текстов запросов и материалов.

**Критерий приёмки (LM06):** widget-тест: урок 3 не завершается без события `save_material` с ID; прогресс сохраняется после перезапуска; урок 7 проходит без пошагового мастера.

### Фаза 7: Приёмка T01–T09 и конкурсный пакет (LM07)
**Цель:** записанные фактические результаты проверок и пакет для сдачи.
- `Builder/integration_test/` — T01 сквозной сценарий против тестового сервера; автоматизировать T03–T07, где возможно.
- Ручные протоколы T01–T09 на реальном устройстве (версия, дата, проверяющий, входные данные, факт, дефекты).
- Инструкция запуска ≤ 10 шагов, паспорт проекта (8 полей), раскрытие моделей, расходов, лицензий и ограничений; синтетические тестовые данные.
- Исправление блокирующих дефектов.

**Критерий приёмки (LM07):** протоколы T01–T09 заполнены, критических дефектов нет, `flutter test` и `pytest` зелёные, release-сборка выбранной ОС устанавливается по инструкции без участия автора.

## 5. Риски и открытые вопросы

| # | Риск / вопрос | Решение |
|---|---|---|
| R-1 | Перенос runtime на сервер — самый крупный объём; клиент без него не проверяется | LM01–LM03 до клиентских фаз; клиент разрабатывается против pytest-контрактов и подменного API |
| R-2 | Выбранные модели нестабильно вызывают инструменты через OpenRouter | Выбрать модели с проверенным tool calling; прототип tool-loop в начале LM02 |
