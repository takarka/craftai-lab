# LM01: серверные агенты и изоляция

**Глубина:** L2. **Статус:** реализация. Основание: фаза 1 плана 01.

## 1. Границы
Агенты, неизменяемые снимки настроек, два скилла, каталог двух моделей,
изолированное хранение данных и прогресса. Runtime и MCP остаются в LM02/LM03.
Чужой и отсутствующий агент дают одинаковый 404. Сброс сохраняет конфигурацию
и прогресс курса, удаляет рабочие данные и увеличивает epoch.

## 2. Оценки
PRD задаёт 20 одновременных пользователей и p95 сохранения до 2 секунд.
Допущение: по одному запросу настроек в секунду на пользователя в пике,
то есть до 20 запросов/с и до 100 активных агентов. При 1000 пользователях
через год — до 5000 активных агентов. Один SQL-сервер достаточен;
отдельный кэш и очередь для CRUD не требуются. Рост истории версий зависит
от редактирования; политику хранения нужно определить до пилота.

## 3. Сейчас
Flutter → FastAPI → SQLAlchemy async → SQLite локально / PostgreSQL в Docker.
Повторно используем Base, get_db, get_current_user и ApiError из app/core.
Схема создаётся через create_all в app/main.py; таблиц Lab пока нет.

## 4. Целевая схема
Клиент → /lab/v1 → транзакция SQL. Источник истины — сервер.
Таблицы lab_*: agents, agent_versions, skills, skill_versions,
agent_skill_overrides, materials, memory_entries, conversations, messages,
course_progress. Все рабочие данные принадлежат владельцу и агенту.
Версия хранит полный JSON-снимок скиллов, их текстов и разрешений.

Контракт использует snake_case: GET/POST /agents; GET/PATCH/DELETE /agents/{id};
POST /agents/{id}/copy и /reset; GET /models и /skills; GET/PUT /course/progress.
POST/PATCH принимают name, task_type, subject, grade, model_id, instruction,
skills [{skill_id, version, instruction_override}], permissions {save_material,
search_materials}. PUT прогресса объединяет completed_lessons и сохраняет
current_lesson и course_version. Инструкция/скилл ≤5000, материал ≤10000.
Валидация Lab возвращает 422, существующие API сохраняют свой контракт.

## 5. Риски
Нужно сейчас: сериализовать изменения одного владельца записью в строку users
перед чтением данных. Это работает между процессами на SQLite и PostgreSQL
и защищает лимит 5, номера версий и сброс от гонок. Дополнительно уникальный
активный слот 1–5 ограничен БД. Локальный mutex не защищает несколько workers.
Копирование переносит только последнюю конфигурацию. Удаление сохраняет
минимальную запись агента для повторного DELETE, освобождая слот и очищая данные.
Поздние записи runtime обязаны сверять epoch под той же блокировкой в LM02.

## 6. Внедрение и наблюдаемость
Добавляются только новые таблицы через существующий create_all; старые API
сохраняются. Каталог скиллов заполняется идемпотентно при старте.
Откат кода оставляет новые таблицы невостребованными. Request-ID и коды ошибок
позволяют диагностировать запрос без записи пользовательских текстов в лог.
Перед пилотом измерить p95 CRUD и частоту 409; PostgreSQL проверить отдельно.

## 7. Открытые вопросы
Q-2: реальные модели не выбраны. Два слота каталога настраиваются через env,
пустые слоты недоступны; совместимость задаётся явно, без вымышленных гарантий.
Вызовы моделей и проверка epoch при поздних событиях остаются в LM02.
Таблицы runs уже появились в параллельной реализации; сброс переводит активные
запуски и ожидающие подтверждения в cancelled в одной транзакции с новым epoch.
Схему архитектуры можно подготовить по запросу.

## 8. Шаги
Модели и схемы → каталог → транзакционный CRUD → тесты изоляции и гонок →
обновление прогресса с фактическими проверками.
