# Постоянное хранение, перенос и восстановление

## Границы этого изменения

Сервер поддерживает PostgreSQL через asyncpg. В окружениях, отличных от `dev`
и `test`, PostgreSQL обязателен: запуск на временной SQLite останавливается
с понятной ошибкой. `postgres://` и `postgresql://` преобразуются в асинхронный
URL; параметр `sslmode` преобразуется в `ssl` для asyncpg.

PR добавляет код и конфигурацию. Он не создаёт облачную БД, не меняет настройки
работающего Render-сервиса и не подтверждает размещение данных в Казахстане.
Выбор хостинга, адрес БД, постоянный файловый том и внешнее хранилище резервных
копий задаются при развёртывании. Для пилота нужно проверить согласованное
размещение БД, файлов, копий и маршрут обработки моделей.

**До слияния и автоматического деплоя в Render:** остановить запись, сохранить
текущую SQLite и файлы, выполнить перенос в постоянную PostgreSQL и задать
`CRAFTAI_DATABASE_URL` в панели сервиса. Без этого новая production-версия
откажется запускаться. Подключение пустой БД не переносит существующие данные.
План Render `free` в `render.yaml` сам по себе не даёт постоянного файлового тома.

## Что хранится где

| Объекты | Хранение |
| --- | --- |
| Аккаунты, агенты, версии, материалы, память, курс, запуски | PostgreSQL |
| Исходные фото и файловые вложения | Каталог `CRAFTAI_STORAGE_DIR` на постоянном томе |
| Копии PostgreSQL | Отдельный том `backup_data` и копия вне хоста |

Текст материалов находится в БД. Исходные фото по-прежнему удаляются по TTL;
резервное копирование не отменяет правила удаления. Пути к файлам находятся
в БД, поэтому при восстановлении файлов нужно сохранить путь монтирования.
JWT-секрет также должен оставаться постоянным между перезапусками.

## Миграции

При запуске API применяется `alembic upgrade head` в транзакции вместо
создания таблиц из изменяющихся моделей. Для PostgreSQL транзакционная
advisory-блокировка сериализует одновременный запуск нескольких процессов.
Начальная ревизия `0001_initial` содержит неизменяемый снимок 23 таблиц.

Ручной запуск из `backend/`:

```bash
python -m app.manage migrate
```

Существующая БД без `alembic_version` автоматически не принимается. После
резервного копирования для совместимой схемы предыдущего MVP:

```bash
python -m app.manage adopt-legacy
python -m app.manage migrate
```

Проверяются таблицы, столбцы, типы, nullable, индексы, внешние и уникальные
ключи, а также имена CHECK-ограничений. Выражения CHECK нужно дополнительно
сверить при принятии вручную изменённой схемы. При несовпадении принятие
останавливается; строки не удаляются и не переписываются. Не используйте
`alembic stamp head` для обхода этой проверки.

Для разработки следующей ревизии:

```bash
alembic revision --autogenerate -m "describe schema change"
```

Сгенерированную миграцию нужно проверить вручную и испытать на копии БД.
`schema_v1.py` не изменяется вместе с моделями. Автоматический downgrade
начальной схемы запрещён: он удалил бы все данные. Откат приложения должен
быть совместим со схемой; восстановление БД выполняется из проверенной копии.

## Перенос SQLite → PostgreSQL

Команды ниже рассчитаны на bash; в PowerShell переменные задаются через
`$env:ИМЯ = 'значение'`. Не передавайте пароли в чат или параметры команд.
Реальные URL сохраняйте только в защищённых переменных окружения/секретах.

1. Остановите старый API и фоновые задания. На время переноса запись закрыта.
2. Сделайте копию исходной SQLite через SQLite backup API и архив каталога
   файлов. Сохраните их вне временного диска сервиса до следующего деплоя.
3. Создайте пустую PostgreSQL-базу. API на ней пока не запускайте: каталог
   скиллов добавит строки и импорт откажется перезаписывать непустую БД.
4. Задайте URL исходной копии и целевой БД. Для SQLite используйте абсолютный
   путь с четырьмя `/`, например `sqlite+aiosqlite:////srv/backup/builder.db`.
5. Запустите импорт и отдельную проверку:

```bash
# Эти переменные заранее задаются в защищённой среде:
# CRAFTAI_DATABASE_URL — целевая PostgreSQL
# CRAFTAI_IMPORT_SOURCE_URL — исходная копия SQLite
python -m app.manage import
python -m app.manage verify-copy
```

Импорт проверяет совместимость схемы, создаёт целевую схему миграциями,
копирует строки одной транзакцией и сравнивает количество и SHA-256 полного
содержимого каждой таблицы. В журнал выводятся только количества строк.
Целевые PostgreSQL-sequence переводятся за максимальные перенесённые ID.
При ошибке записи откатываются; созданная пустая схема может остаться.
Непустая целевая БД никогда не очищается автоматически. Исходная БД читается,
но не изменяется. Запись в неё должна оставаться остановленной до окончания
импорта и сравнения.

6. Восстановите файлы на постоянный том с прежним путём внутри контейнера.
7. Задайте production API постоянные `CRAFTAI_DATABASE_URL`,
   `CRAFTAI_STORAGE_DIR`, `CRAFTAI_JWT_SECRET`, затем запустите API.
8. Проверьте вход, агента, материал, память и курс; перезапустите API и повторите
   проверку. Исходную копию не удаляйте до приёмки и успешного восстановления.

Если схема старой SQLite не совпадает с исходным MVP, импорт остановится.
Для такой БД требуется отдельная согласованная миграция; пропуск таблиц
или молчаливое удаление неизвестных данных не выполняются.

## Docker Compose и резервные копии

Имеющийся Compose сохраняет PostgreSQL в `postgres_data`, файлы — в
`storage_data`. Пересоздание API-контейнера эти тома не удаляет. Команда
`docker compose down -v` удаляет тома и не используется при обновлении.
Стандартные пароли Compose предназначены только для локальной разработки;
для рабочего сервера задайте согласованные `CRAFTAI_POSTGRES_PASSWORD`,
`CRAFTAI_DATABASE_URL` и случайный `CRAFTAI_JWT_SECRET` через секреты.

Для PostgreSQL внутри этого Compose можно включить профиль копирования:

```bash
docker compose --profile backup up -d
docker compose logs backup
```

Сервис `backup` делает первую копию сразу, затем каждые 86400 секунд. Интервал
меняется `BACKUP_INTERVAL_SECONDS` (минимум 60); срок хранения —
`BACKUP_RETENTION_DAYS` (по умолчанию 7, минимум 1). Каталог доступен владельцу
с правами 0700, файлы создаются с umask 077. Копия публикуется после успешного
`pg_dump -Fc` и проверки `pg_restore --list`; при ошибке предыдущие архивы
сохраняются. Старые успешные копии удаляются только после новой успешной.

Однократное создание копии:

```bash
docker compose --profile backup run --rm backup --once
```

Этот профиль подключён именно к сервису `postgres` данного Compose. Для
внешней/управляемой PostgreSQL настройте копирование на её адрес либо
используйте резервное копирование провайдера. Не считайте архив локальной
пустой БД копией внешнего рабочего сервера.

Копии на том же хосте не защищают от потери хоста. Содержимое `backup_data`
нужно регулярно переносить в зашифрованное хранилище вне хоста и наблюдать
за свежестью `.last_success` и ошибками сервиса. Фото/файлы не входят в
`pg_dump`: их том архивируется отдельно при остановленной записи. Внешнее
хранилище и наблюдение не настроены этим PR, так как доступы не предоставлены.

## Проверка восстановления

Восстанавливайте сначала в отдельную пустую БД, сохраняя рабочую:

```bash
# В контейнер PostgreSQL заранее скопирован доверенный архив /tmp/restore.dump.
docker compose exec postgres createdb -U craftai craftai_restore
docker compose exec postgres pg_restore -U craftai --dbname=craftai_restore --exit-on-error --no-owner --no-acl /tmp/restore.dump
```

Задайте `CRAFTAI_IMPORT_SOURCE_URL` исходной БД, а `CRAFTAI_DATABASE_URL` —
восстановленной, затем выполните `python -m app.manage verify-copy`.
При сравнении исходная БД не должна изменяться. Сравнение включает все 23
прикладные таблицы, но не служебную таблицу Alembic; актуальность миграций
проверяется отдельно командой `migrate`.

После сравнения восстановите файловый архив, запустите отдельный экземпляр
API на восстановленной БД и выполните контрольный сценарий. Переключать
рабочий сервер следует после этой проверки.

## Что проверяется автоматически

- SQLite и PostgreSQL 16: весь backend-набор тестов.
- Соответствие замороженной миграции текущим ORM-моделям.
- Принятие совместимой legacy-схемы и отказ при несовместимости.
- Перенос SQLite в целевую БД, полное сравнение, восстановление sequence,
  отказ перезаписывать непустую БД.
- Сохранность агента, прогресса и файлового маркера после нового процесса
  миграций и двух запусков/остановок API в отдельных Python-процессах.
- Настоящие `pg_dump` и `pg_restore` в другую PostgreSQL-базу с полным
  сравнением строк. Это проверка копирования БД, а не всей инфраструктуры.

Документация инструментов: [Alembic async cookbook](https://alembic.sqlalchemy.org/en/latest/cookbook.html#using-asyncio-with-alembic),
[PostgreSQL 16 pg_dump](https://www.postgresql.org/docs/16/app-pgdump.html),
[PostgreSQL 16 pg_restore](https://www.postgresql.org/docs/16/app-pgrestore.html).
