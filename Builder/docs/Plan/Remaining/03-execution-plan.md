Дата: 19.10.2026 (редакция 2). Сводит [Flutter, продукт и выпуск](01-flutter-product-release.md) и [Backend и файловый сценарий](02-backend-files.md) в последовательность с критическим путём. ## Находка по backend

В репозитории `ai-sana` (ветка `feat/builder-backend`, `platform/back/src/Modules/Builder`) есть .NET-бэкенд Builder. По `docs/plan/31-builder-backend-progress.md` готовы: контракты v1 (17 операций, 93 fixtures), auth/сессии, каталог моделей, SSE-шлюз OpenRouter, `POST /builder/search` с защитой от SSRF, read-only MCP, usage/профиль/удаление аккаунта. В модуле Builder нет upload, jobs, artifacts, календаря, планировщика и push. B09 (CI/CD, staging) отложен. Утверждения «исходников backend нет» в планах 01 и 02 относятся к checkout Flutter-репозитория.

## Принятые решения (19.10.2026, владелец продукта)

1. **Файлы — Python-воркер.** Отдельный сервис по образцу `platform/runner` (контейнер на запуск, без сети, read-only, лимиты CPU/памяти/времени, внешний дедлайн, очистка). Сам `platform/runner` не используется: в нём нет библиотек документов, протокол не передаёт файлы, лимиты рассчитаны на ученический код. Образ воркера: `python-docx`, `pypdf`/`pdfplumber`, `reportlab`, лицензированные RU/KK-шрифты. Контракт .NET API ↔ воркер (вход/выход файла, статусы, отмена) описывается в EB-00. Сборку DOCX/PDF можно оставить в воркере; лицензии библиотек проверить в EB-00 (в частности PyMuPDF — AGPL).
2. **Календарь — собственный, на сервере CraftAI, полностью заменяет календарь телефона.** Интеграции с календарём Android/iOS нет; уровень 6 учит работать с календарём Builder. Это отмена прежнего положения «собственный календарь внутри Builder не добавляется» и изменение политики «данные только на телефоне»: события хранятся на сервере (согласие, срок хранения, удаление с аккаунтом, privacy/store declarations).
3. **Автоматизация уровня 7 — серверное расписание.** Раз календарь на сервере, сервер сам читает расписание и запускает Daily Brief и идеи. EB-03 и EB-04 применяются (прежнее решение «локальный best-effort» отменено). Напоминание о занятии — локальное уведомление, запланированное на телефоне из синхронизированных событий (надёжнее фона); готовность AI-результата — push.
4. Уровни 8/9, MCP, голос, зрение — вне выпуска.
5. Звонки/SMS из F01 — исключены из выпуска (подтверждено 19.10.2026); интерфейс и тексты обновить в EF-00.

Решения 1–3 оформить как ADR в `docs/`.

## Модель серверных расписаний (EB-00, EB-03, EF-07)

Daily Brief и генератор идей — шаблоны общего механизма «навык по расписанию», а не отдельные функции. Расписание содержит: навык, параметры и источники, повторение (время, дни, часовой пояс), способ доставки, состояние (включено/пауза) и следующий запуск.

Запуск: планировщик создаёт запуск с уникальным ID (повторный тик не даёт дубль) → сервер собирает вход (для Daily Brief — события дня из календаря Builder) → вызов шлюза модели → результат сохраняется со временем снимка данных и пробелами → затем push «готово». Без push результат виден в приложении.

Границы первой версии (согласовано 19.10.2026):
- Первая версия: только два шаблона, Daily Brief и генератор идей, без свободного создания расписаний из произвольных навыков (решение 19.10.2026). Пользователь меняет параметры шаблона (время, дни, предмет, класс, темы). Механизм на сервере остаётся общим, свободное создание можно включить в следующей итерации.
- Источники: календарь Builder и вводимые параметры. Знания и память остаются на телефоне: на сервер уходит только явно выбранный пользователем фрагмент.
- Лимиты (начальные значения, задаются конфигурацией сервера, уточняются по измерениям до выпуска):

| Параметр | Значение |
|---|---|
| Активных расписаний на пользователя | 2: по одному на шаблон |
| Минимальный интервал | Daily Brief — раз в сутки; идеи — раз в неделю |
| Ручных проб | 5 в сутки на пользователя |
| Токенный бюджет | до 8 000 входных и 2 000 выходных токенов на запуск; до 40 000 токенов в сутки на пользователя |
| Вход запуска | до 100 событий календаря; явно выбранный фрагмент — до 20 КБ |
| Таймаут запуска | 120 секунд; не более 2 повторов |
| Хранение результатов | 30 суток и не более 30 результатов на расписание; всё удаляется с аккаунтом |
| Превышение лимита | запуск пропускается со статусом «лимит», результат не подменяется старым |
- Запуск не выполняет побочных действий (не создаёт события, не вызывает инструменты), только готовит текст.
- Неполный вход фиксируется как «не хватает данных»; запуск не ждёт ответа пользователя.

## Критический путь

Волна 0 → EB-02 + воркер → EF-04/05 → EF-08 → выпуск. Вторая цепочка: EB-06 → EF-02 → EB-03/EB-04 → EF-07. Волны 1 и 2 и серверная часть Волны 3 идут параллельно; Flutter-часть файлов стартует на contract fixtures, которые не закрывают серверную и native-приёмку.

## Риски

- **Объём backend вырос:** вместо одного нового сервиса (файлы) три — файлы с воркером, календарь, планировщик с push. Если выпуск ограничен по срокам, волну 4 можно сдвинуть на следующий релиз без блокировки волн 1–3.
- **Данные учителей на сервере:** события могут содержать имена классов и тем; нужны согласие, минимизация, удаление с аккаунтом, отсутствие содержимого в логах (NFR-OBS-01).
- **Планировщик:** уникальность запуска, пропуски, смена часового пояса, гонки паузы — подробности в EB-03.
- **Push:** нужен провайдер (FCM/APNs) и ключи на сервере; это новая инфраструктура.
- **Python-воркер:** отдельный сервис в эксплуатации; PDF-разбор проверить на 10–20 реальных RU/KK файлах до полной реализации.

## Тесты файловой волны (минимум)

RU/KK-файлы, повреждённые и зашифрованные документы, PDF-сканы (отказ без OCR), чужие и истёкшие file ID, гонки отмены, очистка при ошибке/отмене/удалении аккаунта, отсутствие содержимого в логах (NFR-OBS-01).
