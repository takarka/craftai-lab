# EB-00 — черновик файлового контракта

Дата: 19.10.2026. **Черновик на согласование**, не реализация и не заявление о развёртывании. Закрывает первый пункт Волны 0 [плана выполнения](03-execution-plan.md) (решение D-02 в [04-decisions.md](04-decisions.md)). После согласования переносится в `ai-sana/docs/builder/contracts/v1` (`openapi.json` + `schemas.json`) с теми же соглашениями: Bearer JWT, `ErrorResponse`, типы `Uuid` и `Utc`, поле `x-implementation-status`. Значения лимитов и TTL начальные, задаются конфигурацией и уточняются по измерениям до выпуска.

## 1. Архитектура

```
Flutter ──HTTPS/Bearer──► CraftAi.Api (модуль Builder) ──внутренний HTTP, сервисный токен──► Python-воркер
                              │  владелец, лимиты, статусы, TTL,           (без сети наружу, без секретов,
                              │  очередь, хранилище, вызов модели           без состояния)
                              └──► шлюз OpenRouter (уже есть)
```

- **API владеет всем состоянием:** авторизация, привязка к владельцу, задания, очередь, временное хранилище, TTL, вызов модели. Ключи OpenRouter остаются только в API.
- **Воркер без состояния и без сети.** Две операции: `parse` (файл → структура) и `build` (структура → DOCX и PDF). В модель воркер не ходит. Файлы приходят и уходят в теле запроса, на диске воркера только tmpfs, который чистится после каждого запуска.
- Модель вызывается между `parse` и `build` из API через существующий шлюз.

## 2. Ресурсы и endpoint'ы мобильного API

Маршруты предварительные: сверить с существующей схемой именования (`/builder/...`) в EB-00 и ввести версию, если потребуется.

| Метод и путь | Назначение | Успех |
|---|---|---|
| `POST /builder/attachments` | Загрузка файла (`multipart/form-data`: `file`, `consentRevision`). Заголовок `Idempotency-Key` | 201 `Attachment` |
| `GET /builder/attachments/{id}` | Метаданные и статус вложения | 200 |
| `DELETE /builder/attachments/{id}` | Удалить вложение и всё производное | 204 |
| `POST /builder/document-jobs` | Создать задание. Заголовок `Idempotency-Key` | 202 `DocumentJob` |
| `GET /builder/document-jobs/{id}` | Статус, прогресс, список артефактов, ошибка | 200 |
| `POST /builder/document-jobs/{id}/cancel` | Отмена (идемпотентна) | 202 |
| `DELETE /builder/document-jobs/{id}` | Удалить задание и артефакты | 204 |
| `GET /builder/artifacts/{id}` | Метаданные артефакта | 200 |
| `GET /builder/artifacts/{id}/content` | Скачивание (Bearer, потоком, `Range`, `Content-Disposition`, `Cache-Control: no-store`) | 200/206 |

Публичных постоянных ссылок нет. Чужой, удалённый или истёкший ресурс отвечает `404`, а не `403`, чтобы не раскрывать существование.

### Attachment

`id`, `fileName` (безопасное, не путь), `mimeType`, `sizeBytes`, `status` (`uploaded` | `rejected`), `rejectReason?` (код ошибки, п. 5), `createdAtUtc`, `expiresAtUtc`.

### DocumentJob

Запрос: `attachmentId`, `skill` (`quiz` | `lesson-plan`; закрытый список на первую версию), `parameters` (объект по схеме навыка: тема, класс, число вопросов, язык `ru`|`kk` и т.д.), `outputs` (подмножество `docx`, `pdf`; по умолчанию оба).

Ответ: `id`, `attachmentId`, `skill`, `status`, `progress?` (0–100, подсказка), `artifacts[]`, `error?` (`code`, `message`, `retryable`), `createdAtUtc`, `updatedAtUtc`, `expiresAtUtc`.

### Artifact

`id`, `jobId`, `format` (`docx` | `pdf`), `fileName`, `mimeType`, `sizeBytes`, `sha256`, `expiresAtUtc`.

## 3. Состояния задания

```
queued ──► parsing ──► generating ──► assembling ──► succeeded
   │          │            │              │
   └──────────┴────────────┴──────────────┴──► failed
   └──► canceled (из любого незавершённого)      succeeded/failed/canceled ──► expired
```

Wire-значения: `queued`, `parsing`, `generating`, `assembling`, `succeeded`, `failed`, `canceled`, `expired`. Переходы только вперёд, конечные состояния не меняются. Оборванный ответ модели или частичная сборка — `failed`, а не `succeeded`. Артефакт появляется в списке только когда файл записан и проверен целиком.

## 4. Идемпотентность и отмена

- `Idempotency-Key` (UUID, хранится 24 часа на пару пользователь + ключ + маршрут). Повтор того же запроса возвращает тот же ресурс, другое тело при том же ключе — `409`. Повтор после потери ответа не создаёт второе вложение или задание и не списывает генерацию повторно.
- Один активный `DocumentJob` на вложение; создание ещё одного для того же вложения и навыка при активном первом — `409 job.already-active`.
- Отмена: клиент получает `202`, API отменяет вызов к воркеру и к модели, помечает `canceled`, удаляет промежуточные данные. Отмена конкурирует с завершением: если задание уже `succeeded`, ответ возвращает его фактический статус.

## 5. Ошибки

Тело — существующий `ErrorResponse` (плоский `ApiError` с кодом). Коды файлового модуля:

| Код | HTTP | Когда |
|---|---|---|
| `file.unsupported-type` | 415 | Не TXT/DOCX/PDF по содержимому, а не по расширению |
| `file.too-large` | 413 | Больше лимита размера |
| `file.encrypted` | 422 | Защищённый паролем документ |
| `file.corrupt` | 422 | Повреждён или не открывается |
| `file.no-text-layer` | 422 | PDF без текста (скан); OCR не выполняется |
| `file.partial-text` | 422 | Текстовый слой неполный; политика ниже |
| `file.limits-exceeded` | 422 | Страницы, распакованный размер, объём текста |
| `consent.required` | 409 | Нет актуальной ревизии согласия |
| `job.already-active` | 409 | См. п. 4 |
| `job.model-failed` | 502 | Ошибка или таймаут модели (`retryable`) |
| `job.build-failed` | 500 | Ошибка сборки DOCX/PDF |
| `job.limit-reached` | 429 | Квота заданий пользователя, `Retry-After` |
| `job.unavailable` | 503 | Воркер или очередь недоступны, `Retry-After` |
| `artifact.expired` | 410 | Срок артефакта истёк (метаданные ещё есть) |

Политика смешанного PDF: если текст извлечён менее чем с 80 % страниц, задание отклоняется с `file.partial-text`, а не выдаёт документ из неполного текста. Порог уточнить на реальных файлах.

## 6. Лимиты (начальные)

| Параметр | Значение |
|---|---|
| Размер файла | 10 МиБ |
| DOCX после распаковки | до 50 МиБ, коэффициент сжатия не больше 100:1 |
| Страниц PDF | до 50 |
| Извлечённый текст | до 200 000 символов |
| Контекст в модель | до 30 000 токенов, остальное отсекается с пометкой в метаданных |
| Активных заданий на пользователя | 2 |
| Заданий в сутки на пользователя | 20 |
| Таймаут задания целиком | 180 с; `parse` 30 с, `build` 60 с |
| Воркер | 1 CPU, 1 ГиБ памяти, tmpfs 256 МиБ, без сети, не root, read-only rootfs |
| Размер артефакта | до 20 МиБ |

## 7. Сроки хранения (TTL)

| Данные | Срок |
|---|---|
| Исходный файл | удаляется сразу после успешного `parse`, но не позже 1 часа |
| Извлечённый текст и структура | до завершения задания, не позже 1 часа |
| Артефакты (DOCX/PDF) | 24 часа с готовности |
| Метаданные задания и артефактов | 7 суток |
| `Idempotency-Key` | 24 часа |

При `failed`, `canceled` и удалении ресурса данные удаляются сразу. При удалении аккаунта всё удаляется немедленно и проверяется отдельным тестом. Фоновая очистка идёт с интервалом не более 5 минут и логирует только идентификаторы и счётчики.

## 8. Внутренний протокол воркера

Транспорт: внутренний HTTP/HTTPS в закрытой сети, Bearer-токен сервиса (не выдаётся клиентам). Модель ответов ошибок воркера: `code`, `message`, `retryable`; API транслирует в коды п. 5.

- `POST /parse` — тело: файл (`application/octet-stream`) и `X-Declared-Type`. Воркер сам определяет тип по содержимому. Ответ: `Document` (см. ниже) и признаки: число страниц, доля страниц с текстом, предупреждения.
- `POST /build` — тело: `Document` и `formats`. Ответ: `multipart` с DOCX и PDF либо один выбранный формат; для каждого `sha256`.
- `GET /health`.

`Document`: `title`, `language`, `blocks[]`. Типы блоков: `heading` (уровень 1–3), `paragraph`, `list` (упорядоченный или нет), `table` (строки и ячейки текста). Один и тот же `Document` даёт и DOCX, и PDF, конвертации между форматами нет. Для навыков `quiz` и `lesson-plan` сервер валидирует ответ модели по JSON-схеме шаблона до `build`; невалидный ответ — `job.model-failed`, один повтор с уточнением, затем отказ.

Ограничения воркера: макросы и встроенный код документов не выполняются, внешние ресурсы по ссылкам из документа не загружаются, имена внутри архива не используются как пути, таймаут и память контролируются снаружи процесса.

## 9. Безопасность и данные

- Текст документа — недоверенные данные: в запросе к модели он помещается в отдельную роль данных, инструкции из него не исполняются.
- Проверка владельца на каждом ресурсе; ID — UUID без перебора.
- Логи: только `UserId`, `AttachmentId`, `JobId`, коды, размеры и длительности. Имена файлов, текст и содержимое в логи и телеметрию не попадают (NFR-OBS-01, `LoggingHygieneTests`).
- Скачивание не кэшируется на промежуточных узлах (`no-store`).
- Исходный файл и извлечённый текст уходят в OpenRouter только в объёме, нужном навыку; согласие показывает именно этот путь.

## 10. Согласие перед загрузкой (черновик RU)

> Чтобы создать документ, файл «{имя}» будет передан на сервер CraftAI и обработан там. Нужная часть текста может быть отправлена модели ИИ через OpenRouter. Файл и текст удаляются в течение часа после обработки, готовые документы хранятся 24 часа. Не загружайте файлы с персональными данными учеников.

Казахский перевод — носителем языка (C-06). Ревизия текста передаётся в `consentRevision` и сохраняется вместе с вложением.

## 11. Открытые вопросы для следующего шага

1. Спайк на 10–20 реальных RU/KK файлах: порог `file.partial-text`, качество порядка текста и таблиц, шрифты для PDF.
2. Лицензии: `python-docx`, `pypdf`/`pdfplumber`, `reportlab`, PyMuPDF (AGPL) — выбрать набор без коммерческих рисков.
3. Хранилище: файловая система сервера, объектное хранилище или БД для временных файлов; шифрование «в покое».
4. Очередь: таблица заданий в PostgreSQL с lease (как в Content/PythonReferenceValidation) или внешний брокер; рекомендация — PostgreSQL по аналогии с уже работающей очередью.
5. Выбор шрифтов с кириллицей и казахскими буквами с лицензией на встраивание.
6. Нужен ли вывод только одного формата, или всегда оба.
