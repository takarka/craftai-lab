Дата: 19.10.2026. **Черновик на согласование**, не реализация. Закрывает второй пункт Волны 0 [плана выполнения](03-execution-plan.md): EB-06 (календарь), EB-03 (планировщик), EB-04 (результаты и push). Решения D-03–D-05, D-08 в [04-decisions.md](04-decisions.md). Соглашения те же, что в [файловом контракте](05-eb00-files-contract.md): Bearer JWT, `ErrorResponse`, `Uuid`/`Utc`, `Idempotency-Key` на создающих запросах, `404` для чужих ресурсов, пути предварительные. Значения лимитов начальные и настраиваются конфигурацией.

## 1. Календарь Builder (EB-06)

### Модель события

| Поле | Описание |
|---|---|
| `id` | Uuid |
| `title` | до 200 символов, обязательно |
| `notes` | до 1 000 символов, необязательно |
| `allDay` | `true` — события на целые дни |
| `start`, `end` | для обычного события — локальное время без смещения (`2026-10-19T09:00:00`) и `timeZone`; для `allDay` — даты `2026-10-19` (конец включительно), часовой пояс не используется |
| `timeZone` | IANA-имя (`Asia/Almaty`) |
| `recurrence` | необязательно, см. ниже |
| `reminders` | до 3 значений `minutesBefore` (0–10 080) |
| `subject`, `grade` | необязательные метки предмета и класса — используются шаблонами расписаний |
| `version` | счётчик для оптимистичной блокировки, в ответе также `ETag` |

Хранение: локальное время + IANA-пояс, а не UTC. Так повторяющиеся события не сдвигаются при переходе на летнее время, а all-day события не превращаются в ночные. Для ответов сервер дополнительно считает `startUtc`/`endUtc` каждого вхождения. Несуществующее локальное время (пропуск часа) сдвигается вперёд, неоднозначное (повтор часа) берётся первым вхождением.

### Повторения

Ограниченный набор правил (подмножество RRULE), чтобы не тащить в продукт весь стандарт:

- `frequency`: `daily` | `weekly`;
- `interval` 1–52;
- `byWeekday`: массив `mon`…`sun` (для `weekly`);
- окончание: `until` (дата) или `count` (до 366), либо бессрочно с горизонтом показа 366 дней;
- исключения: `excludedDates[]`;
- переопределение одного вхождения: отдельный ресурс по `occurrenceDate` (другое время, название, отмена).

Месячные и годовые правила в первую версию не входят. Реализация (решение 19.10.2026): собственное разворачивание этого набора без внешней библиотеки — самый быстрый путь, без лицензионных вопросов; Ical.Net можно подключить позже, если понадобятся месячные и годовые правила. Обязательны тесты на переход на летнее время и на границы серий.

### Endpoint'ы

| Метод и путь | Назначение |
|---|---|
| `GET /builder/calendar/events?from&to` | Вхождения в диапазоне (не больше 62 дней, не больше 500 вхождений); у каждого `eventId`, `occurrenceDate`, `startUtc`, `endUtc` и поля события |
| `GET /builder/calendar/events/{id}` | Само событие с правилом |
| `POST /builder/calendar/events` | Создать (201) |
| `PUT /builder/calendar/events/{id}` | Заменить, требует `If-Match` с версией; `412` при конфликте |
| `DELETE /builder/calendar/events/{id}?scope=all\|following&from=` | Удалить событие или хвост серии |
| `PUT /builder/calendar/events/{id}/occurrences/{date}` | Изменить или отменить одно вхождение |
| `GET /builder/calendar/changes?cursor=` | Изменения и надгробия после курсора для офлайн-кэша клиента; пустой курсор — полная выгрузка постранично |

Лимиты: 2 000 событий на пользователя, 5 переопределений на серию в одном запросе не ограничиваем, но общий объём ответа ограничен. Ошибки: `calendar.invalid-time`, `calendar.invalid-recurrence`, `calendar.event-limit`, `calendar.version-conflict` (412), `calendar.range-too-large`.

### Напоминания

Сервер хранит только `minutesBefore`. Само уведомление показывает телефон: клиент планирует локальные уведомления OS по вхождениям ближайших 14 дней и пересчитывает их после каждой синхронизации. На iOS одновременно можно держать ограниченное число запланированных уведомлений (порядка 64), поэтому клиент планирует ближайшие и обновляет по мере приближения. Сервер не гарантирует доставку уведомления и не запускает модель из-за напоминания.

## 2. Расписания AI (EB-03)

### Ресурс `Schedule`

Первая версия: ровно два шаблона. Не больше одного расписания на шаблон на пользователя (`409 schedule.exists`).

| Поле | Описание |
|---|---|
| `id`, `template` | `daily-brief` или `idea-generator` |
| `enabled` | включено или на паузе |
| `timeZone` | IANA |
| `timing` | `daily-brief`: `time` (`HH:mm`) и `weekdays[]`; `idea-generator`: `weekday` и `time` |
| `parameters` | `daily-brief`: `language`, `includeNotes`; `idea-generator`: `subject`, `grade`, `topics[]` (до 10), `ideasCount` (3–10), `language` |
| `extraContext` | необязательно, явно выбранный пользователем фрагмент знаний, до 20 КБ; в ответах владельцу сервер возвращает сохранённый текст либо явный `null`, чтобы правка расписания не удаляла фрагмент |
| `consentRevision` | ревизия согласия на передачу данных |
| `nextRunAtUtc`, `lastRun` | сводка последнего запуска |
| `version` | оптимистичная блокировка |

Минимальный интервал вытекает из шаблонов (сутки и неделя), произвольных интервалов нет.

### Endpoint'ы

| Метод и путь | Назначение |
|---|---|
| `GET /builder/schedules` | Список (до двух) |
| `PUT /builder/schedules/{template}` | Создать или заменить расписание шаблона (идемпотентно), `If-Match` для замены |
| `POST /builder/schedules/{id}/pause`, `/resume` | Пауза и возобновление |
| `DELETE /builder/schedules/{id}` | Удалить расписание и его результаты |
| `POST /builder/schedules/{id}/run-now` | Ручная проба (до 5 в сутки), возвращает `Run` со статусом `queued` |
| `GET /builder/schedules/{id}/runs?cursor` | История запусков |
| `GET /builder/runs/{id}` | Запуск с результатом |
| `DELETE /builder/runs/{id}` | Удалить результат |

### Ресурс `Run`

`id`, `scheduleId`, `trigger` (`scheduled` | `manual`), `scheduledForUtc`, `status`, `statusReason?`, `delivery`, `result?`, `createdAtUtc`, `finishedAtUtc?`.

- `status`: `queued` → `running` → `succeeded` | `failed` | `skipped` | `canceled`.
- `statusReason` для `skipped`/`failed`: `limit` (лимит), `missing-input` (не хватает данных), `missed` (пропущен окно догона), `paused`, `model-failed`, `no-consent`.
- `delivery` ведётся отдельно от генерации: `pending` | `sent` | `failed` | `not-registered` | `suppressed`. Плановое время, начало генерации, готовность результата и доставка — разные поля и события.
- `result`: `format` (`structured`), `sections[]` (заголовок и пункты), `sources[]` (откуда данные), `dataSnapshotAtUtc`, `gaps[]` (например «нет событий на 14:00»), `generatedAtUtc`, `modelCategory`. Результат сохраняется до отправки push. Старый результат не выдаётся за новый: если запуск не удался, `result` пуст.

### Правила планировщика

- Тик каждые 30 с; выбор готовых расписаний через PostgreSQL (`SELECT … FOR UPDATE SKIP LOCKED`) и lease, по образцу очереди в Content. Одна и та же пара (`scheduleId`, `scheduledForUtc`) даёт не более одного запуска (уникальный индекс), поэтому повторный тик или вторая реплика дубль не создаст.
- Время считается в IANA-поясе расписания, переход на летнее время обрабатывается так же, как у событий календаря.
- Догон пропущенных запусков: Daily Brief — не позже 6 часов после планового времени, идеи — не позже 24 часов; позже — `skipped/missed`.
- Конечные повторы: до 2 попыток на запуск, таймаут 120 с.
- Вход Daily Brief собирается на сервере из календаря за выбранный день (до 100 вхождений) и параметров. Знания и память пользователя на сервер не попадают, кроме `extraContext`.
- Запуск не выполняет побочных действий: не создаёт и не меняет события, не вызывает инструменты. Текст событий и `extraContext` передаются модели как данные, не как инструкции.
- Бюджет: до 8 000 входных и 2 000 выходных токенов на запуск, до 40 000 токенов в сутки на пользователя; превышение — `skipped/limit`.
- Пауза: запуск в работе завершается и сохраняется, будущие не создаются. Удаление расписания или аккаунта отменяет запуск в работе и стирает результаты.
- Хранение результатов: 30 суток, не больше 30 на расписание.

Ошибки: `schedule.exists` (409), `schedule.invalid-timing`, `schedule.invalid-parameters`, `schedule.version-conflict` (412), `run.limit-reached` (429, `Retry-After`), `consent.required` (409).

## 3. Устройства и push (EB-04)

| Метод и путь | Назначение |
|---|---|
| `PUT /builder/devices/{installationId}` | Зарегистрировать или обновить: `platform` (`android` | `ios`), `pushToken`, `locale`, `appVersion`; идемпотентно, привязка к пользователю и сессии |
| `DELETE /builder/devices/{installationId}` | Отозвать устройство |

- Logout и удаление аккаунта удаляют устройство. Токен, отклонённый провайдером (недействителен или не зарегистрирован), удаляется автоматически. Один токен в каждый момент привязан к одному пользователю.
- Push только сигнализирует: полезная нагрузка `{type: "run.ready", runId}` и нейтральный локализованный текст («Сводка готова»). Содержимое уроков на экран блокировки не попадает.
- Провайдер (решение 19.10.2026): FCM HTTP v1 для обеих платформ (на iOS через APNs); ключи только на сервере. Для iOS перед реализацией нужны аккаунт Apple Developer и ключ APNs, загруженный в проект Firebase. Точная доставка не гарантируется, результат доступен и без push. Отказ пользователя в уведомлениях даёт `delivery = suppressed` или `not-registered`, но результат остаётся в приложении.

## 4. Данные и согласие

Теперь на сервере хранятся события календаря, расписания и результаты. Всё привязано к владельцу, удаляется вместе с аккаунтом и не попадает в логи (только `UserId`, `ScheduleId`, `RunId`, коды, счётчики). Событие календаря передаётся модели через шлюз при запуске Daily Brief.

Черновик согласия (RU): «Календарь Builder хранится на сервере CraftAI. Для Daily Brief события выбранного дня и ваши параметры отправляются модели ИИ через OpenRouter. Результаты хранятся 30 суток. Не указывайте в названиях событий персональные данные учеников.» Казахский перевод — носителем языка (C-06).

## 5. Влияние на клиент

EF-02 — календарь Builder (список и сетка, создание, правка, офлайн-кэш через `changes`). EF-06 — события с напоминаниями и локальные уведомления. EF-07 — форма параметров двух шаблонов, ручная проба, история запусков, регистрация устройства.

## 6. Открытые вопросы

1. Закрыто: повторения — собственное подмножество (см. п. 1).
2. Закрыто: FCM для обеих платформ. Остаётся проверить наличие проекта Firebase, аккаунта Apple Developer и ключа APNs.
3. Формат `result.sections` (структура и поддерживаемые типы блоков) согласовать с экраном результата и с уроком C-03.
4. Нужен ли обмен событиями между устройствами в реальном времени или достаточно `changes` по запросу.
5. Окно догона 6 и 24 часа принято как начальное (19.10.2026), уточнить после измерений.

## Уточнение EF-07: редактирование и версии (19.10.2026)

`ScheduleDto.extraContext` добавлен в реализацию backend и JSON Schema. Миграции БД не требуется: значение уже хранится в расписании. Клиент подставляет возвращённый текст, а очистка поля явно удаляет фрагмент. Если поле отсутствует в ответе прежнего сервера, сохранение существующего расписания блокируется до обновления сервера; отсутствие поля не трактуется как пустой фрагмент.

Граница текущей реализации по D-05: `daily-brief` и `idea-generator` — встроенные серверные шаблоны, не пользовательские Skills с телефона. Удаление/восстановление локального Skill их не меняет. `Schedule.version` — номер конфигурации для `If-Match`, а не версия навыка. Привязка к версии пользовательского Skill и восстановление серверной версии шаблона остаются открытыми: для этого нужны отдельный контракт снимка исполняемых инструкций, версия и её хранение у запуска. Текущий контракт этого не обещает; добавлять фиктивный `skillVersion` только в клиент нельзя.
