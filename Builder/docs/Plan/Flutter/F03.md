# F03. Реализовать локальную модель данных и изоляцию владельцев

[Все этапы Flutter](README.md) · [Общий план](../flutter-implementation-plan.md)

**Контур:** только Flutter, локальные данные, native-адаптеры, клиентские тесты и мобильная поставка.

**Внешний вход backend:** нет; локальные данные не переносятся на сервер. Получение готового API/отчёта не является серверной работой этого этапа.

**Граница:** здесь не создавать серверные endpoints, БД, gateway, provider config или backend deployment. Если API не готов, использовать явно обозначенные contract fixtures для разработки; живую приёмку оставить заблокированной. Упоминания разделов/ADR/T-сценариев относятся к общему плану.

**Зависимость:** F01/F02, ADR-04/05.

- [ ] F03-01. Описать schema version 1 для workspace, конфигурации, версий, разговоров, traces, документов, памяти, grants и курса.
- [ ] F03-02. Создать repository-контракты и маппинг domain ↔ persistence, не используя backend DTO как таблицы БД.
- [ ] F03-03. Реализовать atomic writes и журнал согласования БД с файлами.
- [ ] F03-04. Ввести owner/installation ID и `workspaceEpoch`; исключить смешивание данных двух аккаунтов.
- [ ] F03-05. Подключить проверенное шифрование/OS file protection и защищённое хранение ключа.
- [ ] F03-06. Реализовать закрытие активного пространства и очистку in-memory caches при выходе.
- [ ] F03-07. Реализовать миграции и recovery screen при ошибке, без скрытого `deleteDatabase()`.
- [ ] F03-08. Обработать нехватку места, недоступный ключ, повреждение файла и прерванный write.
- [ ] F03-09. Создать fixture старой схемы для последующих миграционных тестов.

**Приёмка:** рестарт сохраняет данные; другой аккаунт их не видит; ошибка операции не повреждает активный snapshot; оригиналы и производные материалы защищены и удаляемы.
