# F03. Реализовать локальную модель данных и изоляцию владельцев

[Все этапы Flutter](README.md) · [Общий план](../flutter-implementation-plan.md)

**Контур:** только Flutter, локальные данные, native-адаптеры, клиентские тесты и мобильная поставка.

**Внешний вход backend:** нет; локальные данные не переносятся на сервер. Получение готового API/отчёта не является серверной работой этого этапа.

**Граница:** здесь не создавать серверные endpoints, БД, gateway, provider config или backend deployment. Если API не готов, использовать явно обозначенные contract fixtures для разработки; живую приёмку оставить заблокированной. Упоминания разделов/ADR/T-сценариев относятся к общему плану.

**Зависимость:** F01/F02, ADR-04/05.

- [x] F03-02. Создать repository-контракты и маппинг domain ↔ persistence, не используя backend DTO как таблицы БД.
- [x] F03-03. Реализовать atomic writes и журнал согласования БД с файлами.
- [x] F03-04. Ввести owner/installation ID и `workspaceEpoch`; исключить смешивание данных двух аккаунтов.
- [x] F03-05. Подключить проверенное шифрование/OS file protection и защищённое хранение ключа.
- [x] F03-06. Реализовать закрытие активного пространства и очистку in-memory caches при выходе.
- [x] F03-07. Реализовать миграции и recovery screen при ошибке, без скрытого `deleteDatabase()`.

**Приёмка:** рестарт сохраняет данные; другой аккаунт их не видит; ошибка операции не повреждает активный snapshot; оригиналы и производные материалы защищены и удаляемы.

## Реализация постоянного защищённого хранилища

1. **Реляционная схема V1 (`StorageSchemaV1`):**
   - 18 нормализованных таблиц, охватывающих `workspaces`, `teacher_preferences`, `assistant_configurations`, `instruction_rules`, `assistant_versions`, `conversations`, `messages`, `request_traces`, `knowledge_documents`, `document_revisions`, `knowledge_chunks`, `memory_facts`, `tool_grants`, `pending_actions`, `tool_invocations`, `course_progress`, `quiz_attempts`, `file_staging_journal`.
   - Включён `PRAGMA foreign_keys = ON;` с каскадным удалением для изоляции и очистки.
   - Индексы по `owner_id`, `conversation_id`, временным меткам.

2. **Защищённое хранение ключей и шифрование данных:**
   - `SecureKeyStorage`: аппаратный Keystore / Keychain адаптер на базе `flutter_secure_storage` с генерацией 256-битного мастер-ключа на инсталляцию, а также in-memory адаптер для тестов.
   - `StorageCipher`: аутентифицированное симметричное шифрование (HMAC-SHA256 с 16-байтным случайным IV и 32-байтной аутентификацией целостности) для защиты чувствительных полей и выявления повреждений.

3. **Атомарные транзакции и согласование файлов (`FileStagingJournal`):**
   - Двухфазный коммит через staging-директорию и журнал в БД.
   - Автоматическое восстановление (`recoverInterruptedStaging`) при запуске: удаление повисших staging-файлов и сброс статуса в `aborted`.

4. **Изоляция владельцев и `workspaceEpoch` (`WorkspaceStorageService`):**
   - Разделение данных по `ownerId`.
   - При смене или выходе владельца очищаются in-memory кэши и токены, закрывается контекст.
   - Метод `bumpWorkspaceEpoch` для защиты от устаревших асинхронных операций.
   - Метод `purgeOwnerData` для полного удаления данных аккаунта (ADR-04).

5. **Реализация InitialWorkspaceRepository (`PersistentInitialWorkspaceRepository`):**
   - Проверка `permit.isCurrent` как до транзакции, так и непосредственно перед коммитом.
   - Идемпотентность: повторная запись не перезаписывает и не дублирует существующий workspace.
   - Атомарное создание записей в `workspaces`, `teacher_preferences` и `assistant_configurations`.

6. **Миграции и защита от скрытого сброса:**
   - `StorageDatabase` создает резервную копию базы `.bak` перед миграцией.
   - Ошибки повреждения оборачиваются в типизированное исключение `StorageCorruptionException`.
   - Скрытый вызов `deleteDatabase()` запрещён: повреждённая база сохраняется для восстановления.
