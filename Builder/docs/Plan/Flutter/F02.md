# F02. Создать производственный каркас приложения

[Все этапы Flutter](README.md) · [Общий план](../flutter-implementation-plan.md)

**Контур:** только Flutter, локальные данные, native-адаптеры, клиентские тесты и мобильная поставка.

**Внешний вход backend:** B00: версии контрактов. Получение готового API/отчёта не является серверной работой этого этапа.

**Граница:** здесь не создавать серверные endpoints, БД, gateway, provider config или backend deployment. Если API не готов, использовать явно обозначенные contract fixtures для разработки; живую приёмку оставить заблокированной. Упоминания разделов/ADR/T-сценариев относятся к общему плану.

**Зависимость:** F00, базовые результаты F01.

- [ ] F02-01. Выделить bootstrap, окружения dev/staging/prod и production `App`, сохранив UI Kit.
- [ ] F02-02. Подключить согласованный state management/DI, типизированные ошибки и конфигурацию.
- [ ] F02-03. Настроить маршрутизатор с тремя вкладками, root overlays и auth/onboarding guards.
- [ ] F02-04. Создать repositories/use cases, необходимые для первого вертикального сценария; не создавать пустую архитектуру на все будущие уровни.
- [ ] F02-05. Перенести UI Kit catalog в dev-entry; обозначить fake mode, исключить его случайное включение в release.
- [ ] F02-06. Добавить платформенные capabilities: доступно/недоступно, вместо проверок `Platform.is...` по всему UI.
- [ ] F02-07. Настроить ARB/`gen_l10n` сразу, до размножения строк в экранах.
- [ ] F02-08. Отделить operational config от секретов; API base URL — конфигурация, ключ OpenRouter — никогда клиентская настройка.

**Приёмка:** приложение корректно стартует в каждом окружении, route guards проверяются тестами, UI Kit остаётся доступным разработчику, production не использует его демо-контроллеры.
